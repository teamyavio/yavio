The SDK resolves configuration from multiple sources with a clear precedence order. The first source that provides a value wins.

## Precedence chain

```
Code options → Environment variables → .yaviorc.json → Defaults → No-op
```

1. **Code options** — passed directly to `withYavio(server, { apiKey, endpoint, capture })`
2. **Environment variables** — `YAVIO_API_KEY` and `YAVIO_ENDPOINT`
3. **Config file** — `.yaviorc.json` found by walking up from `process.cwd()`
4. **Defaults** — built-in defaults for `endpoint` and `capture`
5. **No-op** — if no API key is found from any source, the SDK is disabled

## Environment variables

| Variable | Description | Example |
|----------|-------------|---------|
| `YAVIO_API_KEY` | Project API key | `yav_abc123...` |
| `YAVIO_ENDPOINT` | Ingestion API URL. Defaults to `https://ingest.yavio.ai/v1/events`; only set it to point at a self-hosted ingest. | `https://ingest.yavio.ai/v1/events` |

```bash title=".env"
YAVIO_API_KEY=yav_abc123...
# Optional — omit to use the hosted endpoint. Point it at your own ingest when
# self-hosting, or at http://localhost:3001/v1/events when running the stack locally.
YAVIO_ENDPOINT=https://ingest.yavio.ai/v1/events
```

## Config file

The SDK walks up the directory tree from `process.cwd()` looking for a `.yaviorc.json` file. This is useful for local development and monorepo setups.

```json title=".yaviorc.json"
{
  "apiKey": "yav_abc123...",
  "endpoint": "http://localhost:3001/v1/events"
}
```

Place it in your project root or any parent directory. The nearest file wins.

<Callout type="warn">
  Add `.yaviorc.json` to your `.gitignore` to avoid committing API keys.
</Callout>

## Defaults

| Setting | Default |
|---------|---------|
| `endpoint` | `https://ingest.yavio.ai/v1/events` |
| `capture.inputValues` | `true` |
| `capture.outputValues` | `true` |
| `capture.geo` | `true` |
| `capture.rejectedInputValues` | `false` |
| `tools` | none |

## Capture options

The `capture` object controls which data is collected on every `tool_call` event.

```ts
withYavio(server, {
  capture: {
    inputValues: false,  // no input_keys, input_types, input_values, no client metadata
    outputValues: false, // no output_content, no error_message from isError results
    geo: "country",      // country_code, but only { country } in input_values (false: no location at all)
  },
});
```

| Flag | Off means |
|------|-----------|
| `inputValues` | No `input_keys`, `input_types`, `input_values`, no client metadata (`locale`, `country_code`, `region`, `end_user_agent`, `subject_id`), and no `error_message` from a thrown error (messages tend to interpolate the arguments) |
| `outputValues` | No `output_content`. An `isError` result still sets `status` and `error_category`, but its text is not stored as `error_message` (it is output). A thrown error's message is still stored unless `inputValues` is off |
| `geo` | No `country_code` or `region`, no `openai/userLocation` inside the captured `_meta`, and of the rest of `_meta` only known keys (see below) |
| `rejectedInputValues` | Off by default. A call rejected before the handler runs (arguments the schema refused, unknown or disabled tool) keeps the names and types (`input_keys`, `input_types`) of the parameters the tool's schema declares, the `_`-prefixed request context in `input_values`, the client metadata and a value-free reason in `error_message` (McpServer's text as-is when it names only the tool — unknown, disabled — otherwise a fixed "Input validation error" reason), but **no argument values**, no key the model invented and no `output_content`. On: the raw arguments and McpServer's error text are stored |

`geo` takes two more values between "everything" and "nothing":

- `"region"`: `country_code` and `region` (the state or province, as the platform names it — on ChatGPT an English name such as `North Rhine-Westphalia`, not an ISO 3166-2 code) are set, and `openai/userLocation` in the captured `_meta` is replaced by `{ country, region }`. Use it for a breakdown by state or province without city or coordinates.
- `"country"`: `country_code` is set, and `openai/userLocation` is replaced by `{ country }`. Use it when a privacy review asks for country-level analytics only.

In both, city, timezone, coordinates and any field the platform adds to the location object later are not stored; without a valid country the object is removed, and a region only counts next to a valid country. The region is normalised the way ingest does it: typographic apostrophes and dashes folded, at most 64 characters, no digits or `@` (a name that fails is dropped). In city-states the region is the city — ChatGPT reports Berlin as `State of Berlin`, and likewise Hamburg, Bremen, Vienna or Washington, D.C. — so say so if your privacy policy promises "no city". `true` sets `region` too and keeps `_meta` whole.

With any `geo` other than `true` (`"region"`, `"country"`, `false`), the rest of the captured `_meta` keeps exactly `openai/locale`, `openai/userAgent`, `openai/subject` and `openai/session`. Everything else is dropped — ChatGPT's top-level `timezone` and `timezone_offset_minutes`, the conversation and request ids (`sessionId`, `windowId`, `callId`, `itemId`, `openai/request_id`), `traceparent`, `openai/organization`, the client capabilities, and any key the platform adds later, since nothing guarantees a new location field gets a recognisable name. The names of dropped keys (never their values) are stored in `input_values._metaDroppedKeys`, so you can see when a new one appears; a name with a run of 8 or more hex digits is only counted, in `_metaDroppedUnnamed`. The allow-listed request headers in `_requestInfo` are not affected. Before 0.4.1, `"country"` and `false` kept the top-level `timezone`. `geo` has no per-tool override. The React widget's `widget_render` event stores the browser's time zone regardless of `capture.geo`.

Every capture flag fails closed, in `capture` and in a per-tool `tools` override alike: `inputValues`, `outputValues`, `rejectedInputValues`, `tokens`, `retries` and the per-tool `intent` accept exactly `true` and `false`, `geo` accepts `true`, `false`, `"country"` and `"region"`. Any other value (for example the string `"false"` in `.yaviorc.json`, which is truthy) turns that capture **off** and logs `YAVIO-1006` once per flag and process.

Client metadata (`locale`, `country_code`, `region`, `end_user_agent`, `subject_id`) is captured under `inputValues` for every tool, including tools that take no arguments.

`rejectedInputValues` exists because a successful call only ever stores values the tool's schema accepted, while a rejected call would store whatever the model sent. With an enum field such as `plan: z.enum(["basic", "premium"])`, the model may send `"premium, my wife is pregnant"`; the schema rejects it, and with the flag on that sentence is stored. Leave it off if your privacy policy says only fixed values are collected. It has no effect while `inputValues` is off.

`tokens` and `retries` are accepted but reserved — they have no effect today.

## Per-tool overrides

`tools` overrides the capture flags for individual tools, keyed by tool name. A key that is omitted inherits the global value.

```ts
withYavio(server, {
  capture: { inputValues: true, outputValues: true },
  tools: {
    "book-contract": { inputValues: false, outputValues: false, intent: false },
  },
});
```

```json title=".yaviorc.json"
{
  "apiKey": "yav_abc123...",
  "tools": { "book-contract": { "inputValues": false, "outputValues": false } }
}
```

Use this for a tool whose input must never reach analytics — an IBAN, a message body, a birth date. The tool stays on the wrapped server, so it still produces `tool_call` events with latency and status, and `yavio.conversion()` and friends still work from inside its handler. Registering the tool on the unwrapped server instead loses all of that: no `tool_call` event, and tracking calls from the handler are dropped (see [Tracking API](/docs/02-sdk/02-tracking-api#outside-tool-handlers)).

`rejectedInputValues` can be set per tool as well, in both directions.

`intent: false` additionally keeps the tool out of [intent capture](/docs/02-sdk/07-intent-capture): the `context` parameter is neither advertised nor captured for it, and a `context` a client still sends from a cached schema is stripped before validation.

Tool names are not validated — tools register after `withYavio()` runs — so an override for a name that never registers is simply unused. There is no environment-variable form.

<Callout type="info">
  The SDK's PII stripper only matches emails, Luhn-valid card numbers, US Social Security numbers and US-format phone numbers. It is not a substitute for an override on a tool that takes names, addresses, IBANs or dates of birth.
</Callout>

## Example configurations

### Production (Yavio Cloud)

```ts
// Code — just the API key, everything else uses defaults
withYavio(server, {
  apiKey: process.env.YAVIO_API_KEY,
});
```

### Local development

```json title=".yaviorc.json"
{
  "apiKey": "yav_dev_key",
  "endpoint": "http://localhost:3001/v1/events"
}
```

```ts
// No options needed — config file is auto-discovered
withYavio(server);
```

### Disabled (CI / testing)

```ts
// No API key anywhere → no-op mode, zero overhead
withYavio(server);
```
