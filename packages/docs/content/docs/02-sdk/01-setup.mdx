## Installation

```bash
npm install @yavio/sdk
```

The SDK works with either MCP SDK generation as an optional peer dependency: `@modelcontextprotocol/sdk` >= 1.24.0, or `@modelcontextprotocol/server` 2.x.

Hosts that build a new `McpServer` per request (stateless Streamable HTTP, `createMcpHandler`, `mcp-handler`, Skybridge 2) create the client once with `const analytics = createYavio(options)` and call `analytics.wrap(server)` per request; see the package README's "Stateless / per-request servers" section. One difference to `withYavio()`: `wrap()` instruments every tool on the server, including those registered before the wrap, while `withYavio()` tracks only the tools registered through the proxy it returns. Wrapping the same server twice, with either entry point, returns the existing proxy: the first wrap wins and later options are ignored — any differing option (key, endpoint, `capture`, `tools`, `serverOnly`, intent) logs `YAVIO-1108` once.

## Wrapping your server

The `withYavio()` function takes your `McpServer` instance and returns an instrumented version. All tool registrations and connections are intercepted transparently.

```ts
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { withYavio } from "@yavio/sdk";

const server = new McpServer({
  name: "my-server",
  version: "1.0.0",
});

const instrumented = withYavio(server, {
  apiKey: "yav_...",
  endpoint: "https://ingest.yavio.ai/v1/events",
  capture: {
    inputValues: true,
  },
});
```

### Options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `apiKey` | `string` | — | Project API key. Falls back to `YAVIO_API_KEY` env var, then `.yaviorc.json`. |
| `endpoint` | `string` | `https://ingest.yavio.ai/v1/events` | Ingestion API URL. Falls back to `YAVIO_ENDPOINT` env var. Must be `http(s)://`; anything else puts the SDK in no-op mode (`YAVIO-1002`) rather than using the hosted default. |
| `capture.inputValues` | `boolean` | `true` | Capture tool input values, key names and types, plus client metadata |
| `capture.outputValues` | `boolean` | `true` | Capture tool results |
| `capture.geo` | `boolean \| "region" \| "country"` | `true` | End-user location: `true` keeps it as sent, `"region"` keeps the country and the state or province, `"country"` keeps only the country, `false` drops it |
| `capture.rejectedInputValues` | `boolean` | `false` | Store the argument values of calls rejected before the handler runs (by default only their names and types) |
| `tools` | `Record<string, ToolCaptureOverride>` | — | Per-tool overrides of the capture flags (`inputValues`, `outputValues`, `rejectedInputValues`, `intent`) |
| `shutdownTimeoutMs` | `number` | `10000` | Deadline for delivering queued events on shutdown: bounds `shutdown()` and the SDK's own `SIGTERM`/`SIGINT` drain. Falls back to `YAVIO_SHUTDOWN_TIMEOUT_MS`. Set it below the platform's grace period (Cloud Run: 10 s in total; Fly.io: 5 s by default) |

See [Configuration](/docs/02-sdk/03-configuration) for the full precedence chain.

## Auto-captured events

Once wrapped, the SDK automatically captures these events without any additional code:

### Tool calls

Every `server.tool()` and `server.registerTool()` invocation is tracked with:

- **Event type:** `tool_call`
- **Tool name** and input key metadata
- **Latency** (milliseconds, via `performance.now()`)
- **Status:** `success` or `error` — an error when the handler throws (`error_category: unknown`), returns a result with `isError: true` (`tool_error`), when the call fails before the handler runs because the tool is unknown, disabled or the arguments do not match its schema (`validation`, no latency), or when the result fails the tool's own `outputSchema` (`server`)
- **Error message** — the exception message or the `isError` result's text, PII-stripped and clamped to 500 characters
- **Platform** (auto-detected from the connecting client)
- **Inputs** (with `capture.inputValues`, the default) — the arguments, plus the request `_meta` verbatim (`_meta`), the MCP task id (`_taskId`) and five allow-listed request headers with the URL sans query (`_requestInfo`); and the client metadata as first-class fields: `locale`, `end_user_agent`, `subject_id`, `country_code`
- **Output** (with `capture.outputValues`, the default) — the tool result, binary content replaced by size placeholders

<Callout type="warn">
  On ChatGPT the request `_meta` carries the user's approximate location including coordinates and the platform's stable per-user id, and with the defaults both are stored on every tool call. Disclose that collection in your privacy policy, or reduce it with `capture.geo: "country"` (country only, no city or coordinates), `capture.geo: false` (no location) or `capture.inputValues: false` (everything, also available [per tool](/docs/02-sdk/03-configuration#per-tool-overrides)).
</Callout>

### Connections

When a client connects to your MCP server:

- **Event type:** `connection`
- **Session ID** derived from the transport
- **Platform** detected from client signals
- **Client name and version** from the protocol envelope (MCP 2026-07-28), else the `initialize` handshake, else the first product token of the request's `User-Agent` when it has the `name/version` shape (so a stateless host, whose instance never saw `initialize`, still records `openai-mcp` / `1.0.0`; a bare token such as `node` or a library or runtime token such as `Python/3.12 aiohttp/3.9.5` names no client); `metadata.client_info_source` says which. `protocol_version` is the request's `mcp-protocol-version` header
- Emitted at least once per session **per process**: a conversation served by several instances has one connection event per instance. Sessions are counted as distinct `session_id`s, never as connection events

## No-op mode

If no API key is found through any configuration source, `withYavio()` returns the original `McpServer` unchanged. No proxy is created, no HTTP requests are made, and there is zero runtime overhead.

This makes it safe to include `withYavio()` in your codebase unconditionally — it only activates when configured.

<Callout type="info">
  No-op mode emits a `YAVIO-1000` debug log so you can confirm it's active during development.
</Callout>

## Transport behavior

The SDK batches events and flushes them to the ingestion API efficiently:

- **Flush interval:** every 10 seconds
- **Early flush:** triggers at 100 buffered events
- **Buffer cap:** 10,000 events (oldest events are dropped when full)
- **Retry:** up to 5 attempts with exponential backoff (starting at 1 second)
- **Request timeout:** 30 seconds per HTTP request
- **Shutdown:** SIGTERM/SIGINT handlers drain remaining events (`shutdownTimeoutMs`, 10 s by default), then hand the signal back: the SDK removes its listeners and, if it was the only listener when the signal arrived, re-raises the signal so the process exits the way it would without the SDK (128 + the signal number: 130 after Ctrl-C, 143 after SIGTERM). An app with its own handler keeps control; a second Ctrl-C while draining ends the wait. A library that also waits to be the last listener (signal-exit, used by execa and ora) does not get its turn, so handle the signal yourself in that case
- **Your own handler:** wait for the requests in flight, then `await analytics.shutdown()`, then exit. It resolves once ingest has every event queued before the call — the SDK's own drain included, however the listeners are ordered — or at the deadline; a second or concurrent call waits for the first. A `withYavio()` host creates a `createYavio()` client for the same key and endpoint and awaits its `shutdown()`. The README's "Stateless / per-request servers" section has the full pattern

## PII stripping

The SDK strips personally identifiable information (PII) from event payloads before sending:

- Email addresses
- Credit card numbers
- Social Security numbers
- Phone numbers

This runs client-side as a first line of defense. The ingestion API applies the same stripping server-side for defense in depth.
