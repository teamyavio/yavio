## Pulling Latest Images

The simplest way to upgrade is via the Yavio CLI:

```bash
npx @yavio/cli update
```

This pulls the latest Yavio images (dashboard, ingest, docs) and restarts the services. Data volumes are preserved.

To also update third-party images (PostgreSQL, ClickHouse):

```bash
npx @yavio/cli update --all
```

### Manual Upgrade

If you prefer using Docker Compose directly:

```bash
docker compose pull
docker compose up -d
```

## Upgrade the server before the SDK

Upgrade your self-hosted Yavio **before** you bump `@yavio/sdk` in your apps. A newer SDK can send values an older ingest service does not know yet, and ingest rejects such events one by one. The SDK never surfaces delivery errors, so they are lost silently.

<Callout type="warn">
  `@yavio/sdk` 0.4.0 reports tool results with `isError: true` as `error_category: "tool_error"`. An ingest image from before that release rejects every one of those events — so on an old server, tool-reported failures disappear instead of being counted. It also sends `intent_context` on tool calls, which an older ingest silently drops, so the dashboard's coverage split stays empty. Pull the latest images first, then upgrade the SDK.
</Callout>

<Callout type="info">
  `@yavio/sdk` 0.4.1 sends `region` (state or province) on tool calls with `capture.geo` `true` or `"region"`. An ingest image from before migration `0020` drops the field silently; the event itself is stored.
</Callout>

## Checking for Updates

Preview what would be pulled without making changes:

```bash
npx @yavio/cli update --dry-run
```

## Database Migrations

Database migrations run automatically when services start. Both PostgreSQL (via Drizzle) and ClickHouse migrations are applied on boot.

<Callout type="info">
  There is no manual migration step required. Just pull the latest images and restart.
</Callout>

## Version Notes

### ClickHouse 24.3 → 26.8 (one-way)

ClickHouse is pinned to `26.8.26.12`. ClickHouse 24.x no longer receives security fixes.

<Callout type="warn">
  **This upgrade cannot be undone.** Once 26.8 has started on your data, 24.3 refuses to start on the same volume. The only way back is a backup taken before the upgrade.
</Callout>

1. **Take a cold backup of the ClickHouse volume.** Stop ClickHouse only, archive its volume, then continue:

   ```bash
   docker compose stop clickhouse
   VOLUME=$(docker inspect -f '{{range .Mounts}}{{if eq .Destination "/var/lib/clickhouse"}}{{.Name}}{{end}}{{end}}' "$(docker compose ps -a -q clickhouse)")
   docker run --rm -v "$VOLUME":/data -v "$PWD":/backup alpine tar czf /backup/clickhouse-before-26.8.tgz -C /data .
   ```

   ClickHouse's own log tables (`system.query_log`, `system.metric_log` and others) can be most of that volume. To shrink the backup, truncate them before stopping ClickHouse, e.g. `TRUNCATE TABLE system.metric_log`.
2. **Pull and start:** `docker compose pull clickhouse && docker compose up -d`. Migrations run as usual.
3. **Clean up.** The new version, and the system-log retention the compose file now mounts (see below), redefine ClickHouse's log tables. ClickHouse keeps the old ones under a numbered name. List and drop them:

   ```sql
   SELECT name, formatReadableSize(total_bytes) FROM system.tables
   WHERE database = 'system' AND match(name, '_log_[0-9]+$');
   -- then, per table: DROP TABLE system.<name>
   ```

**ClickHouse's own logs** are now kept for 30 days, and the server logs at `warning` level. The settings are in `packages/db/clickhouse/config.d/system-logs.xml`, which `docker-compose.yml` mounts. Previously these tables grew without limit.

### `CLICKHOUSE_ERASER_PASSWORD` is required

The dashboard deletes account, workspace and project data as the `yavio_eraser` ClickHouse user, which can delete rows from the events table and do nothing else. It used to fall back to the unrestricted `default` user when `CLICKHOUSE_ERASER_PASSWORD` was unset. It no longer does: Compose refuses to start without the variable, and the dashboard exits at startup with a message naming it.

If your `.env` predates the variable:

```bash
echo "CLICKHOUSE_ERASER_PASSWORD=$(openssl rand -hex 24)" >> .env
docker compose run --rm migrate   # applies the password to yavio_eraser
docker compose up -d
```

Run the migration before starting the new dashboard, so the password is in place when the first deletion happens.

### Only Yavio's roles can connect to Postgres

Migration `0008` revokes `CONNECT` on the Yavio database from `PUBLIC` and grants it to `yavio_app` and `yavio_api`. Before, any role in the Postgres server could connect just by existing. Yavio's own services are unaffected, and so are the owner (`yavio_service`) and superusers.

If a role of your own connects to the database, a read-only reporting user for example, grant it access after upgrading:

```sql
GRANT CONNECT ON DATABASE yavio TO my_reporting_role;
```

## Rollback

If an update causes issues, you can roll back to a specific image version by pinning the version in your `docker-compose.yml` or using a tagged image:

```bash
docker compose pull dashboard:v1.2.3
docker compose up -d dashboard
```

## Backup Before Upgrading

For production deployments, take a backup before upgrading. With the backup scripts installed ([Backups & Operations](/docs/04-self-hosting/06-operations)), run them by hand:

```bash
sudo /usr/local/bin/yavio-pg-backup.sh
sudo /usr/local/bin/yavio-clickhouse-backup.sh
sudo tail -2 /var/backups/yavio/backup.log   # two "ok" lines
```

A `SELECT … FORMAT Native` export of the events table is not a backup. It loses the materialized views, the users and the row policies.
