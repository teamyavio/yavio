Yavio tracks user journeys through a combination of anonymous sessions and explicit identification. This page explains how identity works and when to call `.identify()`.

## Anonymous sessions

Every conversation gets a session with a `session_id` (format: `ses_` + 21 characters). It is derived from the conversation key the call carries — `Mcp-Session-Id`, ChatGPT's `openai/session`, VS Code's conversation id, the Codex CLI's thread id, or your own [`sessionKey`](/docs/02-sdk/03-configuration#session-key) — so the same conversation has the same `session_id` on every server instance. Without any key it is the connection's own session: one client process on stdio, and on a server that builds a new `McpServer` per request a single call (`session_source: per_request`, not counted as a session). Events are tracked against this session immediately, even before you know who the user is.

"Anonymous" here means *not identified yet*. A `session_id` is still a pseudonymous identifier, so it is personal data under the GDPR and kept only with the raw events: see [Data retention](/docs/07-concepts/06-data-retention).

Anonymous sessions are useful for:
- Measuring overall tool usage and latency
- Tracking conversion funnels before login
- Counting unique sessions per platform

## Calling .identify()

When you learn who the user is (e.g., from an auth token or user input), call `.identify()` to attach a user ID to the session:

```ts
yavio.identify("user_42", {
  plan: "enterprise",
  company: "Acme Corp",
});
```

From this point on, every event in the session includes `user_id: "user_42"` and the provided traits.

### When to call it

Call `.identify()` as early as possible — ideally in the first tool handler that has access to user identity. Common patterns:

- **Auth tool:** if your MCP server has a login or auth tool, call `.identify()` there
- **First tool with user context:** if the AI platform passes a user ID in the tool arguments
- **Every tool (idempotent):** calling `.identify()` with the same user ID is a no-op, so it's safe to call in every handler

## Identity rules

### Immutable user ID per session

The `userId` is set once per session. If you call `.identify()` a second time with a **different** user ID, the call is ignored and a `YAVIO-1302` warning is logged.

```ts
yavio.identify("user_42");     // Sets user ID
yavio.identify("user_42");     // No-op (same ID)
yavio.identify("user_99");     // Ignored — YAVIO-1302 warning
```

This prevents accidental identity conflicts in multi-tool sessions. It is also why a [`sessionKey`](/docs/02-sdk/03-configuration#session-key) must return a conversation id: a key per user would make all of that user's conversations one session.

On a per-request server, `.identify()` carries over to the next call only when the calls share a session key: in a `per_request` session it applies to that one call.

### Additive traits

User traits are merged across calls. Each `.identify()` call adds to (but doesn't replace) existing traits:

```ts
yavio.identify("user_42", { plan: "pro" });
yavio.identify("user_42", { company: "Acme" });

// Session now has: { plan: "pro", company: "Acme" }
```

If the same trait key is set twice, the later value wins:

```ts
yavio.identify("user_42", { plan: "free" });
yavio.identify("user_42", { plan: "pro" });

// Session now has: { plan: "pro" }
```

## User traits

Traits are arbitrary key-value pairs attached to the user for segmentation and filtering. Common examples:

| Trait | Description |
|-------|-------------|
| `plan` | Subscription tier (`free`, `pro`, `enterprise`) |
| `company` | Organization name |
| `role` | User role within their org |
| `signupDate` | When the user first registered |

Traits are included in `identify` events and used for cohort analysis in the dashboard.

<Callout type="warn">
  Avoid storing PII in traits. While the SDK strips known PII patterns (emails, phone numbers, etc.), it's best to use opaque identifiers.
</Callout>

## Retroactive stitching

<Callout type="info">
  Once a session is identified, all its events count for that user. The stored events are not rewritten: events emitted before `.identify()` keep no `user_id`, and on a fleet of stateless server instances only the instance that called `.identify()` stamps it. The dashboard stitches when it reads them.
</Callout>

- **Within the session:** every event of the session counts for the user of its first `.identify()`, the events before the call and the events of every other instance that served the conversation included. A later `.identify()` with another ID never re-attributes earlier events in the users list and a user's detail, and an event's own `user_id` is never overwritten. Counts over a date range (active users, Locations) only look at the `identify` events inside what they read (for active users, the range plus the 30 days before it): a conversation identified before that and again with another ID inside it counts for the later ID there.
- **Not a per-request session:** a session with `session_source: per_request` (a client without a session key on a server that builds a new `McpServer` per request) is one call and is never stitched. A long-lived server that reuses one stateless transport puts every key-less caller into one such session, so one caller's `.identify()` must not count everybody else's calls for that user.
- **Across sessions:** when the platform sends a stable `subject_id` (ChatGPT does), a subject that was identified once is counted as that user in its other conversations too.
- **Where:** the users list and detail, active users, retention, new vs returning, the Locations card, the invocation feed and a tool's recent invocations, and the anonymous statistics. The live feed shows each event's own `user_id`.

## Session lifecycle

1. **First call of a conversation** → session created (`ses_...`), from the conversation's key or the connection
2. **Tool calls** → events tracked against the anonymous session
3. **`.identify()` called** → user ID and traits attached to the session
4. **Subsequent events** → include `user_id` and traits automatically, in the same process (the state is per server process; a session evicted from a busy process's session store starts over)
5. **Client disconnects** → no event; remaining events are flushed on shutdown
