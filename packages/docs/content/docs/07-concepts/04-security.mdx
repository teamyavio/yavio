Yavio is designed with a security-first approach. This page covers how the platform protects sensitive data and prevents abuse.

## PII Stripping

The PII stripping engine runs on every event before it reaches ClickHouse. It is **ON by default** and cannot be disabled in Community or Cloud Free tiers.

### Defense in Depth

PII stripping uses a two-layer strategy:

1. **SDK layer** — a lightweight, non-configurable best-effort pass strips common PII patterns before events leave the developer's process
2. **Ingestion API layer** — the authoritative pass, with the same patterns plus spaced and bare SSNs, ITINs and US street addresses, runs before writing to ClickHouse

This ensures PII is caught regardless of SDK version and provides redundancy if either layer has a bug.

### What Gets Redacted

| Pattern | Detection Method | Replacement | Layer |
|---------|-----------------|-------------|-------|
| Email addresses | `local@domain.tld` in ASCII, lengths bounded as in RFC 5321 | `[EMAIL_REDACTED]` | SDK + Ingest |
| IBANs | Compact or grouped in fours, ISO 13616 mod-97 check (a hex id that happens to pass it is redacted too, [#191](https://github.com/teamyavio/yavio/issues/191)) | `[IBAN_REDACTED]` | SDK + Ingest |
| Credit card numbers | 13–19 digits, optionally separated by spaces or dashes, Luhn check (some 19-digit groupings are missed, [#190](https://github.com/teamyavio/yavio/issues/190)) | `[CC_REDACTED]` | SDK + Ingest |
| US Social Security numbers | SDK: `NNN-NN-NNNN` with any area number (so a dashed ITIN too). Ingest: also `NNN NN NNNN` and the bare nine digits, without the never-issued area numbers 000, 666 and 900–999 ([#193](https://github.com/teamyavio/yavio/issues/193) aligns the two) | `[SSN_REDACTED]` | SDK + Ingest |
| US ITINs | `9NN-NN-NNNN`, spaced or bare | `[SSN_REDACTED]` | Ingest (the SDK only dashed, as an SSN) |
| Phone numbers | Groups of 3–4, 3 and 4 digits, separated by `-`, `.` or a space or not at all, the first optionally in parentheses, with an optional `+CC` or `00CC` and `(0)` in front: the US formats and international numbers of that shape (`+49 171 1234567`, `0171-1234567`, `+49 (0)171 1234567`); and a bare run of 12–15 digits that does not start with 1. There is no E.164 parser: other groupings (`030 12345678`, `+33 6 12 34 56 78`, `0171 123 45 67`) and extensions are not matched ([#189](https://github.com/teamyavio/yavio/issues/189)) | `[PHONE_REDACTED]` | SDK + Ingest |
| Physical addresses | US street addresses: house number, capitalised street name, street suffix (`Street`, `Ave`, `Blvd`, …), optional unit | `[ADDRESS_REDACTED]` | Ingest only |

A card, SSN, ITIN or phone number must stand on its own: a digit run that touches a letter or digit on either side is part of an id, not a number (`deadbeef5551234567`, `order5551234567x`). The exceptions are a run right after a URL percent-escape, a JSON `\uXXXX` escape or a JSON `\b` `\f` `\n` `\r` `\t` escape (`?phone=%2B4917612345678`, `Pay%20with%204111111111111111`, `"Jane\f5551234567"`); a run right after a word of up to 24 letters that has a letter outside a–f, also when that word follows an escape (`Tel5551234567`, `Call%20me%20at%20Tel5551234567`); and a run right after a word of letters a–f only when the number has a phone's shape: a `+`, a `(` or a separator after its first 2 to 4 digits (`cafe555-123-4567`). What remains unredacted, as the price of not cutting hex ids: a number glued to an a–f word without that shape (`cafe5551234567`), to a token of letters and digits, or to a word of more than 24 letters, and one after a double-encoded escape (`%252B…`). A phone number can take an escape's own digits with it (`Call%20me%20at%205551234567` becomes `Call%20me%20at%[PHONE_REDACTED]`): the escape is cut, nothing of the number is left. In ingest, an SSN or ITIN with one separator or none keeps word boundaries instead, so `order_123456789` and `ABC123-456789` stay intact and `ssn_123456789` is not redacted either; the fully separated form (`ssn_123-45-6789`) is. UUID-shaped and traceparent-shaped values standing alone (not glued to a letter or digit, or right after an escape), in any letter case, are masked before these patterns run; a glued one is not (`x21165216-7349-…` becomes `x[CC_REDACTED]-981e-…`). A string that is exactly a valid W3C traceparent is left alone. In the React widget on browsers without regex lookbehind (Safari and iOS before 16.4) the SDK uses the previous patterns instead, which cut ids as SDK 0.5.5 did. Since SDK 0.5.6 and the ingest deployed with it ([#182](https://github.com/teamyavio/yavio/issues/182)); before, the phone and card patterns cut the digits of about 1.8 % of random UUIDs and 0.9 % of hex ids, and ingest cannot restore what an older SDK already replaced.

Known false positives: a standalone 10-digit number, such as an epoch second or `ORD-2026-1234567890`, is redacted as a phone number ([#192](https://github.com/teamyavio/yavio/issues/192)), and so is a 12–15-digit number that does not start with 1, such as an EAN-13; a Luhn-valid 13–19-digit number is redacted as a card number ([#190](https://github.com/teamyavio/yavio/issues/190)), also glued to a word or `_` (`ref_4111-1111-1111-1111`); a fully separated SSN glued to a word is redacted as an SSN (`XBG109-09-1527`); a word right after an escape counts as standing alone, so an encoded path segment like `%2Fuser1234567890` is cut like `/user1234567890`.

Both layers scan all string fields in the event, including nested JSON in `metadata`. Ingest leaves the identifier fields (`event_id`, `trace_id`, `session_id`, `subject_id`) and the timestamp alone: they hold no user content, and a digit run in a random id must not be mistaken for a phone number. They target identity data — business values like prices, cities, dates, and quantities are preserved.

## API Key Authentication

Server-side SDKs authenticate with a **project API key** (`yav_...` prefix). Each project gets a unique key, managed from the dashboard.

- API keys are sent as `Authorization: Bearer <key>` headers
- The ingestion API validates keys against PostgreSQL with an in-memory LRU cache (60s TTL, 10,000 entries)
- Revoked keys are rejected within 60 seconds of revocation

### Key Scoping

Each API key is scoped to a single project within a workspace. A key can only write events to its own project — it cannot read data, access other projects, or perform administrative actions.

## Widget JWT Authentication

Widgets never receive the project API key. Instead, the server-side proxy mints a **short-lived JWT** for each widget interaction:

| Property | Value |
|----------|-------|
| Algorithm | HMAC-SHA256 |
| Expiry | 15 minutes |
| Scope | Single trace ID |
| Permissions | Write-only event ingestion |

### JWT Claims

| Claim | Description |
|-------|-------------|
| `pid` | Project ID |
| `wid` | Workspace ID |
| `tid` | Trace ID (events must match this trace) |
| `sid` | Session ID (shared with the server) |

Even if a widget JWT is extracted from the browser iframe, it is useless after 15 minutes and cannot be used to send events for other traces.

### Trace Validation

Every event in a widget JWT batch must have a `traceId` matching the JWT's `tid` claim. The ingestion API rejects the entire batch if any event has a mismatched trace ID.

## Rate Limiting

| Scope | Limit | Purpose |
|-------|-------|---------|
| Per API key | 1,000 events/second | Prevents abuse from leaked keys |
| Per API key burst | 5,000 events | Allows short spikes (e.g., batch imports) |
| Per IP (unauthenticated) | 10 requests/second | Protects against brute-force key scanning |

Rate limit state is stored in memory. Exceeded limits return `429 Too Many Requests` with a `Retry-After` header.

### Reverse Proxy Requirement

IP-based rate limiting relies on the `X-Forwarded-For` header to identify clients, since the application sits behind a reverse proxy and cannot see the original socket address directly.

Your reverse proxy **must overwrite** (not append to) the `X-Forwarded-For` header with the client's real IP. If the proxy merely appends, a client can send a forged header value to get a fresh rate-limit bucket on every request.

Example Nginx configuration:

```nginx
proxy_set_header X-Forwarded-For $remote_addr;
```

Example Caddy configuration:

```txt
header_up X-Forwarded-For {remote_host}
```

Without this, IP-based rate limits can be bypassed trivially.

## Event Field Size Limits

Individual event fields are validated against maximum size limits to prevent storage exhaustion:

| Field | Max Size | Behavior |
|-------|----------|----------|
| `metadata` (JSON) | 10 KB | Truncated |
| `user_traits` (JSON) | 5 KB | Truncated |
| `error_message` | 2 KB | Truncated |
| `event_name` | 256 chars | Event rejected |
| `user_id` | 256 chars | Event rejected |
| Total event size | 50 KB | Event rejected |
| Batch size | 500 KB | Batch rejected (413) |

Truncation is preferred over rejection for non-critical fields to avoid data loss.

## Pipeline Guarantees

| Guarantee | How |
|-----------|-----|
| At-least-once delivery | SDK retries + ClickHouse deduplication |
| Ordering | Millisecond timestamps + ClickHouse sort order |
| No data loss on restart | Retry with exponential backoff |
| No data loss on shutdown | Synchronous final flush from SDK |
| Backpressure | 503 response when buffer exceeds 100K events |
