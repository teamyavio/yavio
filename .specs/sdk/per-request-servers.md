# Per-Request Servers and MCP SDK v2

**Status:** Implemented 2026-10-20 (#133), review fixes 2026-10-21, multiple processes 2026-10-21 (#142, 0.5.2) · **Packages:** sdk, shared (error code), docs · **Version:** @yavio/sdk 0.5.0 (new API `createYavio()`, peer dependencies changed, `wrap()` instruments tools registered before the wrap) · **Depends on:** [protocol-layer-status.md](./protocol-layer-status.md) (#77), [per-tool-capture.md](./per-tool-capture.md) (#74)

## Problem

`withYavio()` assumed a long-lived MCP SDK v1 `McpServer`. Two kinds of setup broke that assumption.

**MCP SDK v2.** It is not `@modelcontextprotocol/sdk@2` (no such release) but a scoped package family: `@modelcontextprotocol/server` (`McpServer`, `Server`, `InMemoryTransport`, `createMcpHandler`), `core`, `node` (`NodeStreamableHTTPServerTransport`), `express`, `client`. Frameworks that moved to it (Skybridge 2) still depend on v1 as well, so the old peer range was satisfied and npm had nothing to warn about. Against v2 the 0.4.x wrap threw (`server.tool.bind` — v2 has no `tool()`), and behind that throw four more things were wrong: the low-level `setRequestHandler` takes a method **string**, so the protocol layer silently installed nothing (no `tool_discovery`, no validation events, no intent capture); the request `_meta` sits at `ctx.mcpReq._meta`, so sessions, locale and country were lost; an unknown or disabled tool is a **thrown** InvalidParams error, not an `isError` result; the 2026-07-28 protocol era carries the client identity per request in an envelope.

**Servers created per request.** Stateless hosts (the MCP SDK's stateless Streamable HTTP pattern, v2 `createMcpHandler`, `mcp-handler`, Skybridge 2) build a new `McpServer` for every request, so `withYavio()` could only run per request — and every call created a transport with its own flush timer, two process signal listeners, a filesystem walk for `.yaviorc.json`, the mode log lines, a private session store and a private widget-token cache. One transport and two listeners per request leak and soon trigger `MaxListenersExceededWarning`; `yavio.identify()` on request N was invisible on request N+1 of the same conversation (within one process — see "Multiple processes" for what holds across a fleet). The hosted analytics MCP route in this repository runs on `mcp-handler` and was such an integrator.

## Decision

### Shared process-level state (`server/shared.ts`)

Everything that must survive across wraps lives in a module-level registry keyed by the resolved `(endpoint, apiKey)`:

| Shared per key | Per wrapped instance (`createProxy`) | Module level |
|---|---|---|
| the `HttpTransport` (one flush timer, one batch stream) | the connection's own session (calls without a session key off HTTP; a key-less HTTP call gets a state of its own, not stored, #169) | `emittedConnections` — one `connection` per `(apiKey, session id)` |
| `sessions` — the LRU of conversation states (identify, traits, step sequence), keyed by the derived session id | the current MCP transport reference | `emittedToolDiscoveries` — one `tool_discovery` per `(apiKey, tool name)` |
| exactly one `SIGTERM`/`SIGINT` handler pair per process, draining every transport in the registry and then handing the signal back (#138) | `instrumentedTools` — the tools this instance wrapped | `proxiesByServer` — every proxy by the server it wraps and by itself (WeakMap), with the options it was built with, so a second wrap of the same server returns the first proxy |
| | the intent controller | `installedServers` — the low-level servers already patched; the warn-once sets |

**Not shared: the widget token.** Ingest binds a widget JWT's `tid` to the trace id of the call that minted it and rejects a widget batch under any other trace (`WIDGET_TRACE_ID_MISMATCH`), and every tool call has its own trace id. A token is therefore minted per call and never cached — neither across instances (the first version of #133 shared one, which broke every widget call after the first for ~14 minutes) nor across calls on one instance (0.4.x cached per proxy, which had the same effect on a long-lived server's second call). The issue's acceptance item "one mint across instances" was wrong.

**Lifetime.** A key's state is *held* by every `createYavio()` client bound to it (a counter) and *pinned* by the first `withYavio()` call for it. `client.shutdown()` flushes and releases that client's hold; the transport stops and the state is forgotten only when no client holds it and nothing pins it. A `withYavio()` state is never stopped before the process exits (that entry point has no shutdown), and the signal handlers drain everything the registry holds when the signal arrives — an app that exits in its own handler must await `client.shutdown()` first, which waits for that drain (see "Shutdown from the app's handler"). A `401` from ingest stops the transport for that key process-wide (`YAVIO-1203`): every wrap sharing the key stops delivering, which is what an invalid key means.

A hold names the transport's *generation*, so a hold on a transport a signal already drained releases nothing against its successor; a client whose hold is stale re-acquires on its next `wrap()`. Releasing a hold while others remain *drains* the transport (every queued batch, after any send in flight — `HttpTransport.drain()`), not just one flush; the drain is bounded by the releasing client's `shutdownTimeoutMs` (4 s by default since #148; cut to the process deadline once a signal fixed one) like `shutdown()`, and at the deadline it leaves the queue to the timer flush without stopping the transport. The key's state object (sessions, transport facade) outlives its transports: proxies keep it, and a re-acquire after a stop puts a fresh transport behind the same facade, so a re-wrap after the last holder's `shutdown()` — which returns the existing proxy — delivers through the new transport.

**After the signal.** The handler marks the process as draining before it drains the registry. A transport created from then on — by a wrap during the graceful-shutdown window, or by an existing proxy's next `send()` — is *immediate*: it sends on every `send()` (what queues during a send goes with the next one), has no timer, and is awaited only by a `client.shutdown()` that follows (a process that exits without one sends it best effort); bounded by the fetch timeout and the buffer cap, and announced by one `[yavio] Shutdown signal received` line. A wrap after the signal re-acquires the key and reuses the immediate transport the facade already started rather than replacing it, so a send in flight is never orphaned (#142). `HttpTransport.shutdown()` first awaits the batch already in flight, within the same `shutdownTimeoutMs`, and is idempotent: a second `shutdown()` or a `drain()` on a transport that is shutting down resolves with the shutdown's own sends.

**Shutdown from the app's handler (#142).** The canonical handler — `await new Promise((r) => http.close(r)); await analytics.shutdown(); process.exit(0)` — ran against the SDK's prepended listener, which had already cleared the registry and nulled the live transport when the app's `shutdown()` looked for its hold: it found nothing, resolved in 3 ms, and the exit killed the batch in flight (0 of 53 events in the child-process repro, in every ingest setup, in 0.5.0 for the usual listener order and in 0.5.1 for every order). Now `beginProcessShutdown()` keeps its drain in a process-level `signalDrain` promise (accumulated when a signal is handled again), and every `releaseShared()` awaits it first; a stale hold (one the signal drained) then drains the key's current transport — the immediate one a request finishing after the signal sent through — instead of returning; a `shutdown()` without a hold (`settleShared()`: a second call, or nothing re-wrapped since the signal) does the same; concurrent and later calls chain on the earlier one; and each call races the chain against its own `shutdownTimeoutMs` deadline. The #140 hand-back is unchanged: the SDK's listener still records `sole` on arrival, `finishSignal` runs when the drain settles, and an app listener keeps control. `shutdownTimeoutMs` (option, env `YAVIO_SHUTDOWN_TIMEOUT_MS`, `.yaviorc.json`; default 10 s then, 4 s since #148; an integer in [100, 2147483647] — anything else, including a non-integer, a value below 100 ms or one above Node's `setTimeout` limit, is one `YAVIO-1006` warning and the default) bounds each `shutdown()` outside a signal per call, under its own client's value; the drain the SDK starts on a signal runs under the smallest value set explicitly (option, `YAVIO_SHUTDOWN_TIMEOUT_MS` or `.yaviorc.json`) by any client or `withYavio()` call for the key — `resolveConfig()` carries `shutdownTimeoutMsSource` (`option` | `env` | `file` | `default`; a rejected value is `default`), and `acquireShared()` / `pinShared()` register a deadline only when it is not `default`, so an unset participant does not lower the bound (review round 3: every resolved config carries a value, and registering the default capped a 12 s startup client at 10 s next to a plain `withYavio()`); `signalDeadline()` takes the smallest registered one, and `shutdownAllShared()` uses the default when none is set (review round 4: not the transport's own value, which is its creator's and would outlive that creator's release — a 300 ms creator released outside a signal left a default holder's drain bounded at 300 ms) — and a handler's `shutdown()`, which awaits that drain, sees that bound, and is capped by its own client's deadline as well, so raising the drain above the default took `shutdownTimeoutMs` on the shutdown client too, or `YAVIO_SHUTDOWN_TIMEOUT_MS` for the whole process (review round 4; superseded by the process deadline of #148, next paragraph) — the deadline exists to stay under the platform's grace period, which is per process, so the strictest bound wins; `YAVIO_SHUTDOWN_TIMEOUT_MS` counts as explicit for every participant in the process, so it sets one value for all of them (review round 2). The drain is process-wide, so with several keys in one process a handler's `shutdown()` also waits for the other keys' drains, capped by its own client's deadline (review round 3). It is not part of the re-wrap fingerprint. A `withYavio()` host, which has no client, creates a `createYavio()` client **once at startup**, next to its `withYavio()` calls and for the same key and endpoint, uses it only for `shutdown()` and awaits that in its handler: the client's release awaits the same `signalDrain` (documented; an exported process-level awaitable was the alternative). Created inside the handler instead — after `finishSignal` removed the SDK's listeners — `entryFor` would install them again and they would stay (review round 1, finding 8). What the guarantee rests on: the SDK's listener is prepended, so it runs first and its drain is what the app's `shutdown()` finds; the documented exception is an app listener added with `prependOnceListener` after the SDK installed its own, which runs before ours and is gone when the SDK counts listeners, so the SDK re-raises after its drain (#140).

**One process deadline (#148).** The 10 s default ran on three clocks: the signal drain from the signal, a handler's `shutdown()` from its own call, and the post-signal transport's drain after the signal drain settled, with a fresh full deadline — 15–18 s after `SIGTERM` with a 5 s request in flight and a hanging ingest, past Fly.io's 5 s and Cloud Run's 10 s. Now `DEFAULT_SHUTDOWN_TIMEOUT_MS` is 4 s and a signal fixes ONE deadline at signal + D (`SignalCycle.deadlineAt`), where D (`processBudgetMs()`) is the smallest `shutdownTimeoutMs` set explicitly by any live hold or pin across every key, by any `shutdown()` still in progress (`inProgressDeadlines`: a releasing hold keeps its value until its call resolves), or by `YAVIO_SHUTDOWN_TIMEOUT_MS` (read at the signal, so it counts with no participant live), else the default. The signal drain (`shutdownAllShared`) runs every transport's stop under what is left of the budget; every drain or stop a `releaseShared`/`settleShared` causes runs under `boundedBy(own)` — the caller's value cut to the remaining budget, or to D after a hand-back; and `createYavio().shutdown()` awaits its chain through `awaitBounded(work, own)`, which a cycle's deadline timer cuts whether the call started before or after the signal (`deadlineWaiters`); with no time left it returns at once. Values registered after the signal do not move the deadline; a new cycle after a hand-back gets a new one; outside a signal nothing changes but the default. The deadline stops the sending too (`HttpTransport`): at a transport's shutdown deadline the fetch in flight is aborted through the one `AbortController` per fetch that the fetch timeout also aborts (no `AbortSignal.any`, `engines` is `>=20.0.0`), a backoff or `Retry-After` wait that would end at or after the deadline is not scheduled (`canWait`) and the batch counts as lost, `Retry-After` is delay-seconds or an HTTP-date (an unparsable value falls back to the backoff, never to NaN's immediate retry), every timer is unref'd — except, since #164, the deadline of a transport's own `drain()` or `shutdown()` while it runs (`raceDeadline`'s `keepAlive`): it holds the event loop for at most that drain's own deadline and is cleared when the race ends, so a retry that waits out its backoff or `Retry-After` is not cut by Node exiting once the app's server has closed (in 0.5.3 one failed send at the signal lost the whole queue: `shutdown()` never resolved and Node exited with code 0 about 80 ms after the signal); flush interval, fetch timeout, backoff, `Retry-After`, cut and cycle deadlines and the registry's bounded waits stay unref'd, so a host with no drain running still exits on its own. A `shutdown()` outside a signal whose transport has other holders (a `withYavio()` pin, or several clients on one key) runs `drain()`, which has no `canWait` bound: against a failing ingest it keeps the process up for its whole `shutdownTimeoutMs` (measured 30.05 s with an explicit 30 s), even when not awaited, as in 0.5.2 (#164 review round 4); on the signal path `canWait` ends the retries once the next backoff would end past the deadline (about 15 s for D = 30 s) — and a transport created after the signal sends with one attempt, each fetch bounded by what is left of the cycle (`lateFetchBudgetMs()`, read per fetch, 100 ms at least so a send at the deadline is still attempted; after an early hand-back still what is left until signal + D of the last cycle, `lastDeadlineAt`, and D from the send only once that has passed), so a request finishing after the signal still delivers without keeping the process alive past signal + D — a timeout of min(30 s, D) fixed when that transport was created let a send near the deadline hold its socket, and a host without `process.exit()`, until signal + 2D (review round 3), and after a healthy early hand-back a budget of D from the send did the same for a request finishing at signal + 3 s (review round 4); a `shutdown()` after the hand-back waits for it at most D from its call. Loss accounting: every transport counts what a deadline gave up (`deadlineLostEvents()`: queued or in flight at the deadline, refused after it, or a batch whose retry wait would have ended past it — not a batch given up after its last attempt or on an unexpected status, which is a delivery failure with its own `YAVIO-1201` line and must not resurface as a deadline loss at the next signal or exit, review round 2); the cycle prints one `YAVIO-1205` line with the count across every transport, D and the hint, before the re-raise (a POSIX `process.kill` skips `exit` listeners), including what is in flight when the re-raise is about to end the process, plus one more line when it was handed back before its stops settled (a second signal, or its deadline with a stop still settling) — at the deadline when a `shutdown()` is still waiting then, otherwise once its stops have settled — with what was given up since that the first line had not counted — the cycle's only line when the first had nothing to count, as after a second signal well before the deadline next to an app listener; a non-signal `shutdown()` that times out prints its own line; a `process.on("exit")` hook armed only after a signal or a started `shutdown()` prints one line for what was counted after that (an app calling `process.exit()` before `shutdown()` resolved); a plain exit prints nothing. Review round 6: a retry wait the deadline refuses gives up the whole queue with the batch (one count, the drain ends) instead of firing every remaining batch back-to-back with `Retry-After` ignored; the 207 body is read while the fetch timeout and the deadline still cover it, raced against the abort (a body the abort cuts is delivered); a stop already in progress at the signal is cut to the cycle's deadline (`HttpTransport.cutDeadline(atMs)`, never later) and its loss is the cycle's; and the explicit values of live holds and pins live in module-level `holdDeadlines`/`pinDeadlines` that only a release or the test reset clears — not on the registry entry the drain clears — so a second cycle in a process that survived the first still sees them. Review round 7: a stale hold that `createYavio()` replaces on a wrap after the cycle drops its value as a release does (`dropHoldDeadline`), or it counted towards D after the new hold's release; a fetch the deadline or a post-signal budget cuts prints no `YAVIO-1201` line, its loss being the `YAVIO-1205` line's. Review round 10: next to an app listener, a cycle with a stop already in progress at the signal is handed back at its deadline by the cycle's timer — made first in the same run as the stops' deadline timers, for the same duration, so it usually runs first — before the stops have counted what they give up, and those events went to the exit hook's line (or to none if the process was killed first); now the hand-back at the drain's end counts what the cycle's own stops still hold (`markPending(cycle.stops)`: their deadline is the cycle's, so that is what they give up), the late report after they settle reconciles against it (`lostOfMarked`), and the exit hook leaves out what a hand-back line pre-counted (`preCounted`, which replaces the round-2 `pendingInHandBackLine`), so an app's `process.exit()` right after the line adds no second line; the hand-back still comes at the deadline. Rejected: lowering the per-call default only (the close time still adds up), platform detection from env vars (grace periods are configurable and invisible). The README recipe is bounded (`closeWithin(http, 3_000)`: `closeIdleConnections()` every 100 ms, `closeAllConnections()` at the cap — an unbounded `http.close()` waits for the keep-alive socket of the request in flight, 4.5 s with a fetch client and the server's `keepAliveTimeout` behind a load balancer, and `Connection: close` cannot reach an SSE response whose headers are out), on both signals (Fly.io sends `SIGINT`), idempotent (`stopping`), and the child-process fixture runs the README block verbatim (markers `shutdown-recipe:start/end`, an identity test). No SDK export for closing HTTP servers. Budget rule of thumb: `shutdownTimeoutMs` = close cap + 1 s (Fly.io 3 s / 4 s, Cloud Run up to 6 s / 8 s, Kubernetes and ECS 20 s / 25 s).

**Handing the signal back (#138).** Any listener on `SIGTERM`/`SIGINT` replaces Node's default exit for that signal, so an app with no handler of its own kept running after Ctrl-C or `docker stop` once the SDK had drained (0.3.0–0.5.0). The SDK's listener is bound to its signal name (an `emit` without the name is common in harnesses) and *prepended*, so it runs before the app's listeners. When the signal arrives it records whether the SDK was the only listener — the decision is taken then, not after the drain, because an app listener registered with `process.once` is gone by then and that app must not be killed in the middle of its own shutdown. Once the drain is done the handler removes the SDK's listeners and, if it was alone, re-raises the signal (`process.kill(process.pid, signal)`; on Windows, where that is a plain TerminateProcess, `process.exit(128 + n)` instead), so the default exit with code 128 + n (130/143) and the terminal reset happen as they would without the SDK. An app with its own listener keeps control of what happens next: its listener already ran. A second signal while the drain is still running hands back at once — for the signal that arrived, re-raised only if the SDK is its only listener (re-raising the first signal with the first's decision killed an app that handles only the second one, SIGINT say, with SIGTERM's default action mid-shutdown; review round 4) — so an impatient second Ctrl-C ends the process the usual way — unless it is the same signal within 250 ms of the first, which is taken for one delivery arriving twice (`npm run` forwards the terminal's Ctrl-C to a script that already received it, a few milliseconds apart) and is ignored (#148, Decision E) — a wall-clock heuristic, since a listener cannot tell a forwarded signal from a new one: a deliberate second `SIGTERM` within 250 ms is swallowed and the drain runs on to the deadline, a forward delayed past 250 ms on a loaded host ends the drain early with the loss counted in the cycle's `YAVIO-1205` line, and a different signal always hands back at once (documented as such in review round 3, no behaviour change); after a hand-back the state is cleared, so a later wrap installs the listeners again and the next signal drains again, and each cycle carries an identity so a drain that ends after its cycle was handed back cannot end the later one (#148). The signal drain also awaits a transport stop already running outside the signal — the last holder's release — within the process deadline, instead of finding an empty registry and re-raising mid-send (#148). Known limit: a library that also only re-raises when it is the last listener (signal-exit, used by execa and ora) does not get its turn either; such an app handles the signal itself (documented in the README and the setup page). The re-raise is replaceable for tests (`_setSignalReraise`); `signals.test.ts` covers sole listener, unnamed emit, own listener, `once` listener, second signal, re-install after hand-back; the real exit codes (terminated by the signal like a process without the SDK, the app's own code when it handles the signal) were checked on the built dist in child processes for the PR.

**The cycle's line before the waiters (#154, 0.5.4).** The cycle's deadline timer released every `shutdown()` wait before the stops had counted what they give up — it is made first, for the same duration as their deadline timers — so the README recipe's `process.exit(0)` ran before any cycle line, and the exit hook's `Process exit with N events not delivered — await analytics.shutdown() before exiting` counted everything, with a hint for an app that did. Every wait that ends at the cycle's deadline now counts the cycle's line first (`onCycleDeadline`): the cycle's timer, a `shutdown()` wait the cycle bounds (`awaitBounded`; its own timer can run before the cycle's) and the drain's race for a stop in progress; a drain that ends because a stop's own deadline timer cut it (`reachedDeadline()`) counts the same way. Still in flight, the cycle ends there with the round-10 pre-count of what its stops hold. Handed back early by a second signal with its stops still running, its late report comes at the deadline (`late-deadline`) only when a `shutdown()` wait returns there (`appWaits`: an app's own bounded wait, or the cycle's timer or the drain's race while one is in progress) — the released app may exit right away; with none, it waits for the stops as before and holds everything cut by then. A cycle prints one late line (`lateReported`): after one at the deadline, the stops' settling reconciles what it marked and prints nothing, and a loss after it (a send in the deadline's last 100 ms, whose floor outlives the deadline) is the exit hook's — two late lines per cycle were what failed CI on 906ed4e. The line also counts the post-signal fetches the same deadline cuts in the same tick (the recipe's request in flight sent its event through an immediate transport, not through one of the stops): `HttpTransport.precountDue(deadlineAt)` takes the batch in flight whose budget ends by then — not one the 100 ms floor gives longer, not the queue behind it — out of `pendingEvents()`, and its loss, when the cut lands, goes to `precountedLost` instead of `deadlineLostEvents()`, so no later line and not the exit hook count it again. `fetchBudgetMs(now)` takes the fetch's start, so the recorded cut equals the deadline to the millisecond. The exit hook keeps `Process exit with N events not delivered — await analytics.shutdown() before exiting` for an app that exits before its `shutdown()` resolved. The exit hook decides at exit (review round 2), from the latest cycle: no `shutdown()` in progress (`appWaits` 0), the last one to return returned in that cycle and not on its own value outside the cycle's bound (`returnedIn`; a new cycle replaces `lastCycle`; it may have returned earlier in the cycle with its work done), and that cycle's deadline has come by the exit — one of its deadline timers ran (`deadlinePassed`), one of its stops was cut by its own, or a fetch's budget ended at or after it (`HttpTransport` reports each budget cut, not a plain fetch timeout, through `onBudgetCut`; review round 3 — round 2's "a deadline gave something up since the cycle began" also fired on a retry wait refused before the deadline and on an earlier cycle's stops settling late). Deciding when the wait returns was order-dependent: a wait can end because its work settled at the deadline's own cut of a post-signal fetch, before the cycle's timer ran. Then what the exit hook finds is what that deadline left: a late request's batch it cut in flight, the events queued behind such a batch (a late handler's `track()`, `step()` or first `identify()` before its `tool_call`; two late requests on one key), or a send in the deadline's last 100 ms. Its line has the cycle's wording without that hint: `Shutdown deadline of D ms reached — N [more ]events not delivered (in flight when the deadline cut it, sent in its last 100 ms or after it, or queued behind a request it cut)`, "more" only when the cycle printed a line (`printed`; a cycle that ended early and healthy printed none). The counts are unchanged.

`withYavio()` pins the state and creates it on first use; the mode log lines (`Server-only mode`, `Intent capture enabled`) and the no-key warning (`YAVIO-1000`) print once per process. The session LRU's eviction hook still drops the evicted session's connection-event mark (per key).

### `createYavio(options)` → `YavioClient { wrap(server), shutdown() }`

Resolves the configuration **once** (no filesystem walk per request) and holds the shared state. `wrap()` is synchronous and only does what `createProxy` does; it returns the server unchanged in no-op mode and for an unsupported value, and the existing proxy for a server that is already wrapped (or for a proxy itself) — a host that wraps its one long-lived server on every request must not stack a callback wrapper per request (N wraps gave N `tool_call` events per call in the first version). `shutdown()` drains and releases the client's hold (see Lifetime); a wrap after `shutdown()` holds the state again, or starts a fresh transport. **The first wrap wins:** a later wrap of the same server with any differing resolved option — endpoint, key, `capture`, `tools`, `serverOnly`, intent (compared as a stable-JSON fingerprint, `configFingerprint()`) — or a `wrap()` after a `withYavio()` (which would instrument the pre-registered tools), returns the existing proxy unchanged and logs `YAVIO-1108` once per process. `withYavio(server, options)` resolves per call, pins the state and wraps with the same guard — one `createProxy`, two entry points that differ in exactly one thing:

### Tools registered before the wrap — `wrap()` only

A stateless host builds the server — tools included — and wraps the finished server, so the `tool()`/`registerTool()` interceptors never see those registrations. `createYavio().wrap()` walks `_registeredTools` at wrap time and instruments every function-handler tool in place through `RegisteredTool.update({ callback })`, public API on every supported MCP SDK (v1 since the 1.24 floor, v2), with the same callback wrapper, capture flags and intent classification the interceptors apply. `update()` is the only way on v2, whose tools/call executor captured the handler at registration; it also sends `notifications/tools/list_changed` when the server is already connected — one per tool, harmless, and a per-request host wraps before it connects. Task tools (object handlers) stay out, as for the interceptors; a tool whose `update()` throws is skipped and not counted as instrumented, the rest still are.

`withYavio()` keeps the 0.4 behaviour exactly: a tool registered on the raw server before the wrap stays untracked. Integrations that keep a sensitive tool on the raw server on purpose ([per-tool-capture.md](./per-tool-capture.md) documents one) are unaffected on upgrade. Under either entry point a tool registered on the **unwrapped** server *after* wrapping is untracked, and the `tools` overrides are the supported way to limit capture for a sensitive tool — under `wrap()` the only way.

### MCP SDK v2 (`server/extra.ts`, `protocol.ts`, `proxy.ts`)

- The wrapped server is typed by shape — `McpServerLike` (`registerTool`, `connect` required; `tool`, `server` optional) — instead of v1's `McpServer`. The SDK has no runtime import of either MCP package; both are optional peers (`@modelcontextprotocol/sdk >=1.24.0`, `@modelcontextprotocol/server ^2.0.0`).
- `tool()` is bound and intercepted only when it exists.
- `requestMethod()` accepts a method string; the patched `setRequestHandler` wraps the last function argument in every form — `(schema, handler)`, `(method, handler)`, `(method, schemas, handler)`.
- One reader, `readCallExtra()`, maps both context shapes:

| What | MCP SDK v1 `RequestHandlerExtra` | MCP SDK v2 ctx |
|---|---|---|
| session id | `extra.sessionId` | `ctx.sessionId` |
| request `_meta` | `extra._meta` | `ctx.mcpReq._meta` |
| HTTP headers / URL | `extra.requestInfo.headers` (record), `.url` when a string (v1 transports pass a `URL` object, which is dropped) | `ctx.http.req` — a web `Request`: `headers` is a `Headers` object (lower-cased into a record); its `url` is **not read**, so v2 records what v1 records (a path can carry a secret as easily as the query string the sanitiser strips) |
| task id | `extra.taskId` | — |
| client identity | `server.server.getClientVersion()` (initialize handshake) | `ctx.mcpReq.envelope["io.modelcontextprotocol/clientInfo"]` on the 2026-07-28 era, then `getClientVersion()` |

- Status wrapper: a thrown InvalidParams whose text is exactly `Tool <name> not found` / `Tool <name> disabled` (v2) is counted as a `validation` event like v1's `isError` text — same table as [protocol-layer-status.md](./protocol-layer-status.md) — and re-thrown unchanged. A throw that arrives *with* the callback's event in hand came from above the handler (v2's wire validation of the result, `Invalid tools/call result: …`, reached when the protocol layer wraps a handler v2 already stored — tools registered before a `wrap()`): the event is corrected to `status: error`, `error_category: server`, like v1's output-schema failure; a URL elicitation passes through unchanged.
- The widget token's mint is started before the handler runs and awaited after it, so the round trip hides behind the handler; an unused mint (non-object result, handler threw) is dropped, which is why the mint resolves null on every failure (an endpoint that is not a URL included) and never rejects. `resolveConfig()` treats an empty or whitespace-only `endpoint` as unset (the default) and goes **no-op** for a non-empty value that is not an http(s) URL, with one `YAVIO-1002` error — never the hosted default, which would reroute a self-hosted integrator's events and key after a typo.
- The protocol wrappers go around the handler the MCP SDK *stored* (which carries its own request parsing and result validation), on the lazy registration path as on the in-place one, so a wire-rejected result reaches the status wrapper as a throw either way.
- The 2026-07-28 era is negotiated only over Streamable HTTP; `InMemoryTransport` negotiates 2025-11-25.

### Multiple processes (#142)

A fully stateless fleet — N instances behind a load balancer, scale to zero, a graceful `SIGTERM` before every scale-down or redeploy, any instance serves any request — is the deployment the per-request API is for, and everything above is per process. What the fleet gets:

| | Across processes | Per process |
|---|---|---|
| `session_id` | the same for the same key — `Mcp-Session-Id`, `openai/session`, `vscode.conversationId`, the Codex CLI's `threadId`, the integrator's `sessionKey` (derived, not stored; [server-sdk.md §3.7.1](./server-sdk.md#371-session-derivation)) | without any key: over HTTP one call (`per_request`), on every host since 0.5.5 (#169); off HTTP the connection's own session (`connection`) |
| client identity on `connection` | yes: envelope (2026-07-28) > `initialize` handshake > first product token of the request `User-Agent` (`clientFromUserAgent()` in `extra.ts`: `name/version` with at least one digit in the version (`OpenAI/Python 1.40.0` is ∅; whitespace, `;` or the end terminates the token, so `Claude-User/1.0; +Claude-User@anthropic.com` → `Claude-User`, `1.0`, review round 3), or a bare `name` when it is the whole User-Agent (`Claude-User` → name, no version), so a bare first word followed by more — the `Visual` of `Visual Studio Code/1.95` — is never a client (review round 2); the name is then accepted only for a known MCP client — a vendor `isKnownClientName()` in `core/platform.ts` recognises (`openai-mcp`, `Claude-User`, `claude-code`, `cursor`, …) or the explicit allowlist `KNOWN_MCP_CLIENTS` (`mcp-inspector`, `mcp-remote`) — and every other token is ∅: HTTP libraries, runtimes, browsers and server frameworks (`node`, `Python/3.12 aiohttp/3.9.5`, `Java-http-client/17.0.2`, `Nitro/2.9.0`, `Hono/4.6.0`) as well as clients the SDK does not know yet, because a `client_name` lands in the 13-month `stats_daily` client slice, which is never recomputed once the raw rows age out (allowlist replaced the generic-token denylist in review round 5)); `metadata.client_info_source` ∈ `envelope` \| `initialize` \| `user_agent` records which, because a stateless host records the User-Agent's name where a long-lived one records the handshake's (Codex via ChatGPT: `openai-mcp` vs `codex-mcp-client`); `protocol_version` from the `mcp-protocol-version` header, stored only when it matches `^\d{4}-\d{2}-\d{2}$` (a custom transport does not reject other values; review round 1) | — |
| `connection` event | — | at least once per session per process (and again after an LRU eviction): N instances, N rows with random ids and timestamps that never collapse. A `per_request` session: once per process per client — (API key, platform, client name, client version, protocol version, `intent_enabled`) — since 0.5.4 (#144). Read-side rule: sessions are `uniqExact(session_id)` over every event, never connection rows — dashboard queries already did, the #85 statistics job counts connection cells as distinct sessions, `run_query`'s schema doc says so ([event-pipeline.md §6.4](../ingest/event-pipeline.md), [storage-layer.md §5.1.4](../infrastructure/storage-layer.md)). No migration, no backfill, covers every SDK in the field. Rejected: deterministic ids in the SDK (it does not know the project; one conversation on two apps would collide in the stats prelude's cross-project `LIMIT 1 BY event_id`; keying on the API key duplicates on rotation; old SDKs keep random ids), ingest dedup with storage, an ORDER BY change (table rebuild over 13 months) |
| `tool_discovery` | — | once per tool per process; harmless: ingest writes it to `tool_registry` (`ReplacingMergeTree(updated_at)`, read with `FINAL`), so N reports are one row and `registered_at` means "last reported" |
| `identify()`, traits, step sequence | — (#145: read-side stitch, timestamp-ordered funnels) | the per-key LRU; one `identify` event per session state, so one per instance that serves the conversation (0.5.4); `YAVIO-1302` per process, best effort |
| mode log lines, `YAVIO-1000`, `YAVIO-1108` | — | once per process, so N per fleet |
| shutdown | — | each process drains its own queue; see "Shutdown from the app's handler" |

### Session keys of session-less clients (#144, 0.5.4)

A stateless transport issues no `Mcp-Session-Id`, and MCP 2026-07-28 removes the header (SEP-2567). Until 0.5.4 every call without it or `openai/session` fell back to the proxy's connection session, which on a per-request host is new for every request. Measured on 0.5.3 (mock ingest, 50 `tools/call` from one client, MCP SDK v1 1.32.1 and v2 2.3.1): 50 `tool_call`, 50 `session_id`s and 50 `connection` events on v1 stateless, v2 `createMcpHandler` in the 2025 era and in the 2026-07-28 era, and v1 with an auth middleware setting `req.auth`; with `openai/session`, 1 and 1. The Sessions KPI and the users list counted a session per call, paths were empty, the live feed showed a connection per call, `identify()` never carried over, and the anonymous statistics counted a key-less caller as one person per call — enough to admit a free-text `event_name` (threshold 5) into a table kept indefinitely.

What clients send on `tools/call` (verified in client source unless noted, October 2026):

| Client | Sends | Usable key |
|---|---|---|
| ChatGPT | `_meta["openai/session"]` (documented) | yes (`openai_session`) |
| VS Code ≥ 1.105 / Copilot Chat | `_meta["vscode.conversationId"]`, `vscode.requestId`, `traceparent` | yes (`vscode_conversation`) |
| Codex CLI (`codex-mcp-client`) | `_meta.threadId`, `sessionId`, `callId`, `x-codex-turn-metadata`, on every server | yes (`codex_thread`), Codex only |
| Claude Code 2.1.309 | `_meta["claudecode/toolUseId"]` (per call), configured headers | no |
| claude.ai connectors | `User-Agent: Claude-User`, `x-anthropic-client`; OAuth if configured | none known (absence not proven) |
| Cursor | `_meta.progressToken` only (forum report quoting the client) | no |
| Zed | no `_meta` | no |

`authInfo` exists only where the host's middleware sets `req.auth`, and its layout is the integrator's; `authInfo.clientId` is the OAuth client, shared by every user of a client app — neither a user nor a conversation.

Decided (#144): the two built-in client keys (VS Code from any client, Codex only from `codex-mcp-client`; the rest deferred until a client sends a conversation key), the `sessionKey` option (`SessionKeyRequest = { headers, meta, authInfo, extra }`, synchronous, fallback only, guarded — `YAVIO-1102` once per process, `YAVIO-1006` for a non-function — stored as `deriveCustomSessionId()`, a keyed HMAC), `session_source` on every server event (migration 0022; a bounded string in the schema, ingest NULLs unknown values), one `connection` per process per client for `per_request` sessions, and the read-side exclusion (Sessions KPI with a hint, users `totalSessions`, the statistics job's individuals and connection cells). The key must name a **conversation**: a per-user key (an auth subject) chains every conversation of that user into one session, which the one-user-per-session rule (`YAVIO-1302`) and the per-session funnels and paths of #145 would then treat as one endless journey. Measured on 0.5.4 with the same probe: key-less, 50 `tool_call` labelled `per_request` and 1 `connection` on all four hosts; `sessionKey` from a header (v1 and v2 2026-07-28), `vscode.conversationId` and the Codex `threadId` (User-Agent `codex-mcp-client/0.164.0`): 1 session and 1 `connection`; the same `threadId` from User-Agent `node`: `per_request`.

Widget events (review round 1): a per-request session's widget rows carried no `session_source` and counted as one more person per session in the statistics — five sessions with a widget `track()` of a free-text name admitted it. The server now injects `sessionSource` with the widget config (`_meta.yavio`) and the React SDK stamps it on every event it sends, so those rows follow the same rules; widgets on SDKs before 0.5.4 send NULL and count as before.

Out of scope: a `sessionKey` override mode (it is a fallback only), built-in keys for Claude, Cursor and Zed, auth-derived keys inside the SDK, `sessionKey` in the hosted analytics MCP route (it becomes `per_request`; its Sessions KPI drops to about 0 with the hint, expected). #145 must ignore `per_request` sessions.

### Fail closed (`YAVIO-1107`)

A value without a `registerTool` and a `connect` function (the two methods the proxy binds) is returned unwrapped with one `console.error` per process, decided in `withYavio()` **before** the configuration is resolved — no transport, no listeners. `createYavio().wrap()` makes the same decision before it touches the shared state (so a `wrap(notAServer)` after `shutdown()` re-acquires nothing), and both entry points run it in no-op mode too.

## Compatibility

- **Peer dependencies:** both MCP peers are optional. An app that installs neither gets no install-time warning and a `YAVIO-1107` at runtime if it passes something that is not an `McpServer`.
- **`withYavio()` behaviour is unchanged**, including for tools registered before the wrap. `createYavio().wrap()` is new and instruments those (see above). Release note.
- **Widget tokens are minted per tool call** in non-serverOnly mode (0.4.x cached one per proxy instance, see above): one `POST /v1/widget-tokens` per tool call that returns an object, bounded by a 2 s abort (`token.ts`), after which the result is returned without `_meta.yavio` and `YAVIO-1103` is logged once. `serverOnly: true` mints nothing. Release note.
- **Wrapping the same server twice** returns the existing proxy instead of instrumenting it twice; the second call's options are ignored (`YAVIO-1108` once when any of them differs).
- **Connection and discovery dedup are per API key and per process**: two projects in one process each get their own `connection` and `tool_discovery` events; two processes serving one conversation each emit their own (see "Multiple processes").
- **`createYavio().shutdown()`** delivers everything queued before the call (the signal drain included), then releases a hold; it stops the transport only when nothing else uses it. Bounded by `shutdownTimeoutMs` (option since 0.5.2): its own client's value outside a signal, from the call; at or after a signal, the process deadline signal + D (#148: D the smallest explicit value across every key, hold, pin, `shutdown()` in progress and the env var, else 4 s), whichever comes first.
- **The `connection` event's `client_name`** can now come from the request's `User-Agent` (0.5.2); `metadata.client_info_source` tells the sources apart, and `protocol_version` is set from the `mcp-protocol-version` header where it was never set before.
- A client that sends no conversation key to a per-request host gets one session per request, labelled `per_request` since 0.5.4 and not counted as a session (since 0.5.5 every key-less HTTP call on any host, a long-lived server that reuses one stateless transport included, #169); VS Code and the Codex CLI are keyed by their own conversation ids, and `sessionKey` covers the rest (#144, above).
